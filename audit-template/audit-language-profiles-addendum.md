# General Audit Addendum — JavaScript/TypeScript and JVM Profiles

This file is a required companion to `audit-template-v3-polyglot.md` for the repository's intended general-audit coverage. Apply the core audit method first, then apply every profile in this addendum that is materially present in the target. These are risk prompts, not mandatory findings; do not penalize a target for mechanisms, runtimes, frameworks, or artifact types it does not use.

Preserve the same evidence standard as the main audit: distinguish confirmed defects from coverage gaps, verify reachability and actual behavior before reporting material findings, prefer repository-declared tools and versions, and do not install or mutate global tooling without authorization.

## JavaScript / TypeScript profile

Record the supported runtimes and versions (for example Node.js, Bun, Deno, browser engines, edge/worker runtimes, Electron, or framework-managed runtimes); package manager and lockfile; module system and package type; TypeScript/JavaScript language targets; `tsconfig`/`jsconfig` inheritance and project references; workspace/monorepo layout; bundler/transpiler/minifier; framework; test/lint/type-check tooling; native addons; generated code; package exports/imports; and produced server, client, library, CLI, desktop, extension, worker, or bundled artifacts.

Check module/package correctness: ESM versus CommonJS behavior; conditional exports/imports; package `type`; extension and resolution rules; path aliases that work in type checking but not at runtime; dual-package hazards; circular imports; import-time side effects; tree-shaking assumptions; dynamic imports; plugin/module discovery; workspace symlinks; source-versus-built resolution; and differences between development, test, bundled, and installed-package execution.

Check type/runtime correctness for TypeScript: material `any`/`unknown` leakage; unsafe assertions and non-null assertions at trust boundaries; incorrect narrowing; declaration/runtime divergence; generic/variance errors; unsound external declarations; stale generated types; runtime validation missing where untyped data enters typed code; `skipLibCheck` or broad suppressions that hide project-relevant failures; and whether emitted JavaScript actually matches the supported runtime target. Do not treat stricter compiler options as universal requirements; evaluate the project's declared policy and risk.

Check asynchronous and concurrency behavior: floating/unhandled promises; lost rejections; incorrect `await`; cancellation and `AbortSignal` propagation; timers/intervals; event-listener lifecycle; stream backpressure and cleanup; socket/HTTP/database/request lifecycle; worker threads/web workers; child processes; queues; race-prone shared mutable state; AsyncLocalStorage/request-context leakage; shutdown/drain ordering; retry storms; and unbounded parallelism. Validate framework-specific lifecycle behavior rather than assuming Node semantics apply to every runtime.

Check common semantic hazards: prototype-chain/property injection and unsafe object merging; surprising coercion and equality behavior; `this`/binding mistakes; sparse arrays; mutation of shared objects; iterator/generator misuse; date/time/time-zone assumptions; numeric precision and integer-boundary errors; regex backtracking; Unicode/encoding behavior; JSON serialization edge cases; stale closures/state in UI frameworks; and memory retention through listeners, caches, closures, timers, or long-lived module state.

Check security-sensitive runtime behavior according to actual trust boundaries: `eval`/`Function`/dynamic template execution; command construction and child processes; SSRF-capable URL fetching; path traversal and archive/file handling; unsafe redirects; prototype pollution; DOM/XSS sinks and HTML/script injection where browser-rendered content exists; server/client secret separation; authentication/session/cookie handling when applicable; native addons; runtime permission/sandbox models; and source-map or diagnostic leakage. For framework-specific server actions, RPC layers, loaders, or server components, verify authorization and input validation at the real server boundary rather than assuming the framework enforces application policy.

Check package-manager and supply-chain behavior: lockfile consistency; workspace resolution; mutable or git/file dependencies; overrides/resolutions/patches; lifecycle scripts (`preinstall`, `install`, `postinstall`, `prepare`, and equivalents); package-manager configuration; registry/source overrides; executable package hooks; vendored/prebuilt native binaries; dependency advisories; typosquatting/confusable package risk where evidence warrants it; and whether clean installs reproduce the expected dependency graph. Inspect repository-controlled install/build hooks before executing them.

Check tests and quality gates using repository-supported commands: unit/integration/browser/end-to-end tests; runtime-specific tests; TypeScript checking when configured; project lint rules; async-test cleanup; fake timer restoration; test isolation from order/time/locale/environment/network/global/module state; deterministic browser/runtime coverage; and representative error/cancellation/shutdown behavior. Treat coverage percentage as supporting evidence, not a quality score by itself.

Check frontend/bundled artifacts where relevant: client/server code separation; accidental server secret/config inclusion; source maps; development/debug code; dead-code elimination; tree shaking; code splitting; asset/resource paths; cache/version behavior; hydration/SSR equivalence; CSP-relevant emitted behavior; bundle size and duplicated dependencies; browser target compatibility; and runtime feature/polyfill assumptions.

Check package/library publishing where applicable: `exports`, `imports`, `main`, `module`, `types`, declaration maps, files/package inclusion, side-effects metadata, dual ESM/CJS behavior, entry points/subpaths, semver/public API compatibility, consumer TypeScript compatibility, install from the packed artifact rather than only the source tree, and accidental inclusion of tests, credentials, configuration, source maps, or private files.

For Electron, Tauri, Node native addons, WebAssembly hosts, or other native bridges, apply the relevant native/FFI profile as well. Verify renderer/main or host/guest trust boundaries, IPC validation, sandbox/context-isolation settings where applicable, native library loading, ABI/runtime compatibility, callback/lifetime ownership, and packaging of native components.

Prefer repository-declared commands and pinned tools. Where configured and available, use the project's test runner, TypeScript compiler, ESLint or other declared lint tooling, package-manager integrity/advisory commands, and representative build/package commands. Do not introduce a new formatter, linter, type checker, bundler, package manager, or runtime merely because it is common in the ecosystem.

## Java / Kotlin / JVM profile

Record supported JDK/JVM versions and vendors when relevant; Java/Kotlin language versions; Gradle/Maven or other build system; wrapper and plugin versions; module/multi-project layout; dependency locking/catalogs; annotation processors/KSP/KAPT/code generation; target bytecode level; framework/runtime; test/static-analysis tooling; JNI/JNA/native libraries; packaging mode; and produced JAR/WAR/module image/native-image/container-entry artifacts when in scope.

Check Java/Kotlin interoperability and type contracts: platform types and nullability across Java/Kotlin boundaries; generic variance/raw types; boxed versus primitive behavior; equality/hash/compare contracts; data-class/record semantics; collection mutability and view/copy assumptions; checked/unchecked exception boundaries; reflection-generated contracts; generated sources; and public API/ABI compatibility where libraries are consumed independently.

Check concurrency and lifecycle behavior: threads/executors/fork-join pools; virtual threads where used; coroutines, dispatchers, scopes, structured concurrency, cancellation, supervisor behavior, and blocking calls from coroutine contexts; `CompletableFuture`/reactive pipelines; synchronization/locks/atomics; thread interruption; ThreadLocal/coroutine-context cleanup; request-context leakage through pooled threads; shutdown hooks; executor ownership; timer/scheduler cleanup; deadlocks; starvation; retry storms; and unbounded task/queue creation.

Check resource and error handling: try-with-resources/`use`; streams/readers/writers; files/sockets/HTTP/database connections/result sets; process lifecycle; partial initialization; suppressed/causal exceptions; broad catch-and-ignore behavior; interruption preservation; transactional rollback; and cleanup across exceptional or cancelled paths.

Check runtime/dynamic behavior: reflection; dependency injection scanning; proxies/bytecode generation; classloader/module-layer/plugin isolation; dynamic class/resource loading; service loaders; scripting/expression engines; serialization/deserialization; runtime type activation; and configuration that exposes diagnostics or weakens verification. For app servers, plugin hosts, test runners, and hot-reload environments, verify classloader and ThreadLocal/static-state cleanup across reload/redeploy boundaries.

Check JVM-specific security and parsing risks according to reachability: native Java serialization; unsafe polymorphic deserialization or type activation in Jackson/Gson/Kryo/XStream or equivalent libraries; XML external entities/entity expansion; expression/template injection; archive/path traversal; subprocess construction; URL/SSRF behavior; TLS/provider configuration; authentication/session framework integration; actuator/admin/debug endpoints; JMX/JDWP/remote-management exposure; and JNI/JNA/native boundaries.

Check dependency/build integrity: Gradle/Maven wrapper provenance and version; plugin repositories; dependency repositories and mirrors; dynamic/ranged/snapshot versions; dependency locking/verification where the project relies on it; local/composite builds; generated build logic; buildSrc/plugins; annotation processors; Maven/Gradle lifecycle hooks; dependency conflicts and shading/relocation; duplicate classes/resources; transitive advisories; and reproducibility of a clean build without relying on undeclared local caches.

Check performance and availability risks: accidental quadratic collection/stream operations; unbounded caches/queues/executors; excessive allocation and boxing; regex backtracking; recursion/deep parsing; blocking I/O on constrained pools/event loops; connection-pool exhaustion; thread leakage; classloader/metaspace leaks; ThreadLocal retention; direct/native memory; GC-pressure pathologies; and framework/runtime settings that materially change latency, memory, or failure behavior. Do not prescribe collector/JVM tuning without workload evidence.

Check tests and quality gates using repository-supported commands: unit/integration/application tests; Gradle/Maven verification tasks; Kotlin/Java compiler warnings; project-declared static analysis such as Error Prone, SpotBugs, Checkstyle, PMD, detekt, or equivalent; coroutine/concurrency tests; framework test slices versus full integration; resource cleanup; deterministic time/locale/environment behavior; and representative packaged-artifact smoke tests.

Check artifacts and compatibility: manifest/module metadata; main class/entry point; service-provider/resource inclusion; multi-release JARs; signed JAR expectations when in scope; shading/relocation; duplicate/conflicting dependencies; bytecode target compatibility; runtime/JDK assumptions; container/runtime flags when part of the supported local artifact contract; debug symbols/metadata leakage where material; and behavior from the packaged JAR/WAR/image rather than only IDE/source execution.

For GraalVM Native Image, JNI/JNA, Panama/FFM, embedded native libraries, or other native integration, also apply relevant native artifact/FFI checks. Verify reflection/resource configuration, initialization timing, native library search/loading, ABI/layout, ownership, callbacks, exception/error translation, and actual emitted native hardening where applicable.

Prefer repository-declared wrapper commands such as `./gradlew` or `mvnw` when present. Do not silently replace the project's build system, JDK, formatter, analyzer set, dependency policy, or framework conventions merely to satisfy the audit.

## Score calculation integrity

When the main audit requires weighted score arithmetic and a calculator, shell, scripting runtime, spreadsheet, or equivalent deterministic arithmetic tool is available, compute the score mechanically rather than estimating it mentally. Preserve the category scores, applicable positive weights, excluded/N/A categories, renormalization basis, unrounded result, and final rounding rule so another reviewer can reproduce the total.

Do not silently round intermediate values. If deterministic calculation tooling is unavailable, show the arithmetic explicitly and lower confidence in the numerical total if it cannot be independently checked. A mathematically precise total does not increase substantive audit confidence when the underlying evidence is weak.

## Final verification additions

Where applicable, include these profile-specific checks in the main audit's **Ecosystem-specific** final verification results:

- **JavaScript/TypeScript:** supported runtime matrix; module/package resolution; repository-declared tests/type checks/lint; promise/cancellation/listener/stream/process lifecycle; lockfile/install-hook/dependency behavior; server/client trust boundaries; representative build/bundle/package output; sourcemap/secret leakage; published-package entry points/exports/types; and native-addon/Electron/worker boundaries when present.
- **Java/Kotlin/JVM:** JDK/language/build-tool matrix; wrapper-based build/tests; Java/Kotlin nullability/interoperability; thread/executor/coroutine/cancellation behavior; resource and ThreadLocal/classloader lifecycle; dependency/plugin resolution; serialization/reflection/dynamic-loading boundaries; packaged JAR/WAR/image smoke behavior; and JNI/JNA/native-image boundaries when present.
